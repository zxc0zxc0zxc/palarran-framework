# Resolve conflicts with an explicit target

`/palarran:git:conflicts {target-branch}` integrates the named target into the owned feature branch under the project's merge/rebase policy. Read the [shared Git contract](README.md), feature spec/contracts and relevant ADRs. This does not approve merging an MR, pushing changes or rewriting shared history. `--plan` does not fetch or begin an integration.

Resolve repository, source branch/current SHA, exact target ref and remote without inventing a branch name. Inspect existing in-progress operations and ownership. A local target branch can be used when explicitly requested; a remote target requires the authorized targeted fetch and observed fetched SHA. Never treat a stale tracking ref as verified current state, run pull implicitly, fetch all unrelated remotes, or print credential-bearing URLs. Record source, target and merge-base SHAs and whether remote freshness is observed or NOT_RUN.

Before starting, protect staged/unstaged/untracked work. Do not stash/reset/clean it automatically. Use the already authorized clean owned worktree or continue a known owned conflict operation; unrelated dirt in a shared checkout is a reason to isolate the integration. Preserve the original feature branch/base for existing work. Prefer merge when required by policy; rebase only where the policy and actual user scope permit its history rewrite, especially for a published/shared branch.

Inspect all unmerged index entries and base/ours/theirs versions, plus the intent of both changes and their tests/decisions. In rebase, ours/theirs labels refer to the rebase operation's sides, not necessarily the developer's intuitive branch ownership; identify actual commits rather than choosing a word. Handle rename/delete, binary, mode, submodule and generated/lockfile conflicts explicitly; do not combine lockfiles with a blind text union. Regeneration requires the trusted project toolchain and existing execution scope. If unavailable, preserve an explicit unresolved gate.

Resolve the business behavior, not just marker text. Keep both compatible requirements, propose a reasoned alternative for incompatible ones, and ask a precise business-policy question when evidence cannot decide. Do not select an entire tree with ours/theirs, silently drop a target security fix or invent an expected behavior. Record the semantic resolution before dependent edits.

Review the resolved diff and staged tree, ensure no unmerged index stages remain and inspect introduced conflict-marker patterns with context (fixtures/docs may intentionally contain examples). Absence of textual markers alone is insufficient. Run relevant regression, contract and integration checks against the exact combined subject. A syntactically valid result may still violate one side's requirement; include cases for both and a combined case.

Finish the known local merge/rebase only after its stage gates and ownership review, following [commit](commit.md) for a merge commit or a subsequent stage. If the target branch moves again, state which SHA was integrated rather than claiming permanent conflict freedom. On failure preserve the operation/status and explain what remains. Do not abort an operation started by another actor or reset to a remembered SHA automatically. An authorized abort of this skill's own operation still requires checking preservation limits: Git documents that abort may not reconstruct earlier uncommitted work.

Record resulting commit(s), source/target/merge-base, resolution decisions, actual checks and remaining integration gaps in the target plan/private handoff. Local integration is neither a remote push nor a production readiness verdict.
