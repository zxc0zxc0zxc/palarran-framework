# Prepare and publish an MR or PR

`/palarran:git:mr {target?}` prepares a concrete review description for the actual feature diff. Read the [shared Git contract](README.md), the host/project MR template and actual authorization. In GitLab call it an MR; in GitHub call it a PR. Discovery of a remote is not permission to push or publish. With preparation-only scope, complete the local title/body and evidence first and report the remaining publication step; no platform mutation is needed to make the draft reviewable.

Resolve source branch and exact HEAD, intended target ref/observed target SHA, remote host and any existing MR for this same subject through authorized read scope. Use the actual comparison base/merge base and inspect all committed changes plus any uncommitted work excluded from the proposed MR. A feature's earlier draft, different target or another branch's MR is not the current subject. Do not create duplicate MRs after an uncertain response: reconcile source/target/author and platform result first.

Lead with the concrete problem and resulting behavior; use a short actual before/after example when it helps. Rewrite an outdated title/description around the final diff instead of appending the conversation history. Prefer one or two concise paragraphs for a simple change; honor additional project template fields. The [inert MR template](../templates/mr.md) supplies the owner's mandatory sections, not permission to claim they passed:

- **Environment:** exact new/changed variable names; required/default/secret scope, affected environment and rollout actions. Names and public non-secret behavior only, never values, populated env files or credential-bearing endpoints. State “None” explicitly when evidence shows no env changes; otherwise mark the inventory unknown.
- **Testing:** prerequisites and test identities/data, concrete reviewer scenarios with expected behavior, actually observed commands/checks with subject, and FAIL/NOT_RUN gaps. Do not substitute “tests pass” or a CI badge for scenarios; a local fixture/mocked check stays identified as such.
- **Production readiness:** ready, conditional or not ready, with evidence-based reasons. Cover migrations/data compatibility, environment dependencies, deployment/rollout/rollback and blockers; use reasoned N/A when absent. Green local tests alone do not prove deployment readiness, operational SLA or completed production verification.

Include Feature and relevant ADR IDs without private journal contents. Distinguish implemented/integrated/verified/deployed states and exact source revision. A report or HTML artifact can supplement the MR but does not replace these fields or independent acceptance. Reviewer assignment, notifications, comments and merge actions require their actual user scope; do not add them as an automatic publishing side effect.

When push/publication is authorized, push only the intended branch using the trusted existing remote and inspect the observed remote head. Do not force-push, alter branch protection or use secrets in argv/body. Use a structured API body or a private body file for multiline CLI text, never shell interpolation. Creation/update must return a real platform result; capture and read back the URL/source/target/title/body. Do not claim a published MR from a CLI timeout or a locally written Markdown file. Attach every created GitHub PR to the current task using the host attachment tool when available; if unavailable, retain its verified URL and report attachment NOT_RUN. Do not attach unrelated reference PRs.

Record private draft path, exact source/target, observed local/CI/platform checks, returned URL or publication NOT_RUN, readiness and remaining actions in the target handoff. Publication does not merge, deploy or authorize a production change. Unknown platform outcomes are reconciled before retrying; local evidence and pending remote work remain distinct.
