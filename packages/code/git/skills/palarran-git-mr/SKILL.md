# Prepare the review handoff

Start with the [task context entry](../../../../core/agents/docs/task-context.md). Read the [selected Git guide](../../docs/mr.md), relevant [Git contract sections](../../docs/README.md) and [source rows](../../docs/sources.md). Consult only [Git domain scope](../../../../core/agents/docs/domain-contracts.md#git-workflows), [feature lifecycle](../../../../core/agents/docs/feature-lifecycle.md) when feature identity/branches matter, [compact decision records](../../../../core/agents/docs/decision-memory.md#small-scoped-reviews) and [short memory entry](../../../../core/agents/docs/global-memory.md#short-entry). Reuse one task summary/index across related skills; do not require ADR/context/handoff files for a small read-only review.

Resolve source/target/remote and actual draft/create/update scope. An explicit publication request supplies its concrete authorized scope; do not ask again for already granted permission. Preparation-only scope completes a reviewable local draft first. `--plan` is offline local inspection/inert drafting: no fetch/push/platform calls, Git mutations or application checks. This skill never automatically merges, deploys or messages reviewers.

1. Pin source HEAD, target ref/SHA/freshness and comparison base. Inspect the full committed diff, excluded dirty work, plan/ADRs and actual local/CI evidence. In authorized platform read scope reconcile an existing same-subject MR before creating another; no invented URL or stale-subject checks.
2. Write a concise concrete problem/result title and description, adapting the final state to the host template. Include mandatory **Environment** (names, required/default/secret scope, rollout; explicit None only after review), **Testing** (prerequisites, reviewer scenarios/expected behavior, actual checks and FAIL/NOT_RUN gaps) and **Production readiness** (ready/conditional/not ready with migrations, compatibility, rollout/rollback and blockers). Never include secret values/raw logs or infer readiness/SLA from local green tests.
3. Include Feature/relevant ADR IDs and exact subject without private journal contents. Preserve implementation/integration/verification/deployment distinctions. Record rationale before dependent decisions and prepare all concrete draft/evidence work before requesting any genuinely missing publication scope.
4. If publishing is authorized, use only the intended normal branch push/platform action and inspect remote/platform results. Preserve hooks/protection; no force-push or shell interpolation. Use structured bodies/private body files. After timeout reconcile actual remote head and existing MR before retrying. Read back returned URL/source/target/title/body; until confirmed, report publication NOT_RUN/UNKNOWN rather than success. Attach created GitHub PRs to the task through the available host tool, or report attachment NOT_RUN with the verified URL.
5. Save draft/URL, exact subjects, decisions/index/handoff, readiness and remaining checks in target `.palarran/git/<task>/`, prose following `languages.docs` and public project conventions. Verified portable learning is separately owner-policy/privacy bound. MR creation does not grant merge, deployment, comments, notifications or access to unrelated repositories.
