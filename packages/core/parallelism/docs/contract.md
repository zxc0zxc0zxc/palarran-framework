# Parallel execution contract v001

Specification: automatic parallelism / Temporal v0.3, 2026-10-24. This is an implementation contract, not a claim of optimal scheduling or live provider acceptance.

## Admission and context

A trusted planner turns an ordinary request or skill into the same bounded manifest. It supplies a stable run_id, plan_version, exact base_commit, total tokens/cost_micros/launches/seconds budget and separately reserved integration_tokens, verification_tokens and handoff_tokens. Tasks contain task_id, parent_task_id, goal, acceptance, depends_on, plan_version, base_commit, contracts, files, resources, tools, actions, limits, owner, worktree, session_id and expected_result. Optional task_queue binds a task to an approved Temporal execution queue; this is a non-secret opaque alias, never an endpoint or credential. Optional budget_phase selects execution (default), integration, verification or handoff. Reserved tokens and monetary pools are spendable only by explicitly registered tasks in that phase; children inherit their parent phase. Use explicit integration_cost_micros, verification_cost_micros and handoff_cost_micros for the frozen estimate. When absent, each defaults to the corresponding fraction of the frozen token allocation, rounded down; the remainder belongs to execution. This is a conservative scheduling heuristic, not provider pricing evidence. Report the resolved allocation and review it for the actual model rates. Reserves are not discarded or secretly added to the total. No full parent transcript is copied. Pin required AGENTS, decisions, contracts and artifact hashes in the packet. Project authority precedes retrieved content.

The dispatcher validates rather than invents decomposition. Useful parallelism requires independent ready work, nonoverlapping file/resource ownership, explicit contracts and remaining root budget. A small first wave grows only while ready work and capacity exist. Native delegation that cannot be observed/accounted/cancelled is disabled in managed autonomous mode. Backend is immutable for a run and all descendants. Active continuation uses the same run ID and plan digest; changed configuration cannot migrate an unfinished run.

## Durable execution

Private local SQLite serializes admission across dispatcher instances. Whole path prefixes and named resources are exclusive across active/unknown work. Code writers require distinct absolute worktree paths. An attempt reserves its full limits before launching, and no new process receives a new budget. Submitted work is implemented, not accepted. Dependencies require independent verified results for the exact subject. Integration remains explicitly owned, sequential work with its own verification task.

Transitions: pending → ready → running → submitted → verified. blocked, handoff_pending, failed, cancel_requested, cancelled and unknown remain distinct. Duplicate starts/events do not launch an existing attempt. A coordinator tick marks a heartbeat older than the immutable heartbeat_seconds (default30, allowed1–300) unknown. Read-only status/dashboard requests never mutate leases; a stopped coordinator needs an operator/Worker tick before reconciliation. Heartbeat loss means unknown, retains reservations/claims and requires explicit terminal proof plus usage reconciliation before another assignment. No automatic retries of model/Git/external side effects. Cancellation propagates through the run and reports unknown until every process proves termination. Cost uses integer micro-USD; tokens, actual known spend and outstanding reservations are separate. Unknown is never zero. All attempts remain durable.

## Verification and progress

Adapter receipts bind subject, usage and terminal proof. A separate verifier must supply independent=true, matching subject and nonempty evidence; a zero exit does not establish acceptance. Final business acceptance is an explicit final task depending on all implementation tasks, with its independent verifier. A planner must supply it when the desired outcome requires integration. The shared run report exposes remaining tasks and immutable plan hash; source plan progress is updated through an explicit coordinator-owned export, never inferred from worker prose.

## Limits

One private SQLite authority serializes all admission. [Scoped authority transport](authority.md) lets developer-machine workers use the same root ledger and independent verifier. Temporal distributes scheduling; never clone the SQLite ledger per worker. Protected cross-machine transport and exact artifact delivery require target-specific acceptance. No automatic live harness, paid call, deploy or remote worker registration. Local fake adapters prove dispatcher behavior, not model quality or operational SLA. Comparable benchmarks report time to accepted result, tokens, micro-USD, conflicts and rework with fixed tasks and verifier, never speedup from incomparable runs.

Trusted in-process callbacks must cooperate with heartbeat/cancellation and return bounded results. Python threads cannot forcibly preempt arbitrary callback code; hard process time/output limits require the supervised Native/Headless adapters. Their command allowlists and registered worktrees still do not constitute OS/network isolation.

Integration budget slots use dispatch_mode=external and are excluded from automatic ready assignment. Only their configured queue coordinator claims them. Known negative gate receipts can satisfy an operation-accounting task while the queue remains blocked; a separate final/acceptance task requires all combined semantic gates to pass. Never equate an observed negative result with business acceptance.

Predeclared unused repair slots may set required_for_completion=false only with external dispatch. They consume no launch/spend until claimed and cannot block completion merely by remaining unused. Any attempted running, failed or unknown stage still participates in root status/accounting. At least one required acceptance task remains; the final business acceptance slot is required. A child cannot downgrade its parent completion requirement. Spare slots and final acceptance aliases must be frozen before execution; no replay of a previously attempted acceptance slot.
