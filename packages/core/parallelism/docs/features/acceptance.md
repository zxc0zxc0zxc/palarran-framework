# Independent acceptance and ordered release

## Four evidence levels

1. Local service tests/static checks/migration and invariant checks.
2. Producer plus every consumer contract checks, including semantic expectations.
3. End-to-end business scenarios through real interfaces of the exact isolated composition with synthetic data.
4. Transition checks for every allowed old/new producer/consumer combination, migration prefix and flag setting.

Freeze independent criteria before implementation. Verifiers must not modify expected values to fit the implementation. Verdicts are `PASS`, `FAIL`, `INCONCLUSIVE`, `NOT_RUN`; unavailable environments are never `PASS`. A hash binds bytes, not truth or independence. Trusted check registrations and actual result channels remain required.

For referral rewards cover success, no qualifying action, duplicates, concurrent processing, temporary consumer failure, late delivery, reversal/compensation, cross-user/tenant access and recovery after partial execution. A green unit suite across all repositories can coexist with a failed reward amount or currency invariant.

## Immutable subject

Bind every result to feature/spec/plan/contracts, exact commits for every participating service, test-suite hash, environment configuration hash, synthetic-data version, migration identities and flags; include image digests when available. Never store secret values in the composition. Preserve previous compositions and failed receipts. Changing any pin creates a new identity and conservatively invalidates readiness. Explicitly proven independence may be supported later; no implicit reuse is allowed.

## Safe release prefixes

Freeze migration/deployment/flag/observation order, owner, allowed predecessor/successor compositions, numeric stop thresholds, observation duration and recovery evidence. Each intermediate composition must pass the applicable compatibility protocol. Mark code/schema/data/external-action reversibility independently. An irreversible data or external action needs a forward-repair plan, not a fictional universal rollback.

`release_ready` means evidence and a valid plan for the current composition. `accepted` requires an actually authorized release and the required observation evidence. The runtime coordinates trusted target-specific bindings and records outcomes; there is no default shell deploy or automatic SSH. Check environment drift immediately before applying a step. Persist intent before the action, deduplicate event/operation identities and reconcile unknowns before further work. Failure or a threshold breach stops progression and reports the responsible owner and retained liabilities.

The offline three-repository referral example is an executable acceptance fixture. It establishes protocol, budgeting and deterministic mismatch detection on local test services, not production deployment, live SLOs, model quality or physical multi-machine behavior.
