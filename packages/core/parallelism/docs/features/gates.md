# Independent feature gates and referral laboratory

Feature PAL-20261024-F37A91; specification v0.1; ADR core/2026-10-24-cross-repository/0001.

A coordinator registers a bounded Python checker before execution, including script SHA256, criteria SHA256, verifier identity, captured defaults/closures and owning source-file hash and an external verification task in the original Dispatcher run. Scripts run through the existing supervised process-group runner with a minimal environment, bounded output and deadline. Raw output is hashed rather than persisted. A zero exit completes a check process; a separate exact receipt verifier validates its actual structured verdict, complete composition and criteria. No worker-supplied PASS is accepted.

A failed or inconclusive business gate can have a verified accounting task: this means the failure was independently observed, not that the feature passed. Immutable check receipts bind the complete canonical composition, run/check IDs, exact commits, registered suite hash, criteria and evidence. The suite pins grader code, bounded captured JSON data and the owning source file; its imported dependencies and global bindings remain a trusted immutable host responsibility. New commits require new checks; predeclared spare external task slots consume the same root budget. Unknown termination or spend retains the original reservations and requires reconciliation.

The executable laboratory creates three new local Git repositories (auth, cards, ledger), launches synthetic implementations through real loopback HTTP interfaces and exercises successful eligibility, ineligible actions, duplicate/concurrent deliveries, temporary consumer failure, late events, reversal, tenant isolation and recovery after partial completion. It intentionally starts with a cents/major-unit mismatch: local service checks pass but the independent business check fails. A new committed repair creates a new composition and all four gate levels rerun. Transition checks launch the actual baseline and each ledger → auth → cards commit prefix, with enabled and disabled flag paths. The release plan binds those exact matrices and state hashes; the demonstration stops at release_ready.

Run `python3 -m packages.core.parallelism.feature_demo --output /absolute/new/private/path`. Existing output paths are rejected. No existing project repositories, model APIs, installs, cloud resources, production deploys or credentials are touched. Generated reports are private and keep safe case identifiers, verdicts, hashes and usage, never raw service logs. The capability-owned `fixtures/features/check.py` and `service.py` ship with the laboratory; frozen checker copies remain separate from mutable generated service repositories. The supplied synthetic services are trusted local test programs; a loopback process is not a security sandbox.

This follows [Google SRE release engineering](https://sre.google/sre-book/release-engineering/) and [Pact provider verification](https://docs.pact.io/provider), checked 2026-10-24: isolated/local checks do not establish business compatibility, and exact versions matter. The laboratory demonstrates its frozen synthetic protocol only. Real applications need project-specific independent gates, authentication, migrations, rollout matrices and observability.

The runner passes `feature_binding={composition_id,check_id,criteria_sha256}` to `Dispatcher.claim_task`. The authority validates current composition, criteria and the selected frozen slot inside the same reservation transaction; a stale or misbound request cannot reserve spend. Gate callbacks receive deep copies of frozen criteria, and returned proof is frozen before validation. Host registries and dependency code remain trusted; this is not an arbitrary Python sandbox.
