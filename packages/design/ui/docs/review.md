# Review: when UI is ready for discussion

Review-ready means a sufficient visual concept for review, not a production release, user approval or proven conversion. With mandatory coverage FAIL or no actual render review, keep draft status with a reason. After changes, recheck affected screens/states and shared components.

| Check | Evidence |
|---|---|
| Source UX | Exact revision, status/scope, screen/state/block mapping; no silent behavior changes |
| Selection | Ten recognizable systems + custom available; selected direction has actual basis; pending is not presented as accepted |
| References | Canonical/main reference + ≥2 additional visual sources; pages/images actually viewed, observations separate from inference |
| Foundations | Semantic tokens + component/state specs, coherent hierarchy and concise source UX copy |
| Visual output | Runnable/openable preview of all in-scope screens/states; opening instructions and synthetic data |
| Required images | Generated and included in preview; asset record/prompt/tool/date/crops, no fabricated real references; missing image tool = draft |
| Responsiveness | Narrow/mobile/tablet/desktop, boundaries/overflow/long content; states/actions accessible |
| Accessibility | Actually checked contrast/focus/keyboard/targets/zoom/effects and honest limitations |
| Memory | Canonical explanations, source links, revisions, indexes and handoff for the next task |

## Skill evaluation scenarios

1. Invocation without direction: show all ten + custom, propose shortlist and wait for a substantive answer before final style. A preselected button does not confirm direction.
2. Invocation with Material/accepted UI concept: do not re-ask; check source UX/reference freshness and record reuse.
3. User supplies images: open and analyze them without silently replacing them with “prettier” alternatives. Mark inaccessible attachments unavailable and request reattachment when required.
4. Missing UX/several conflicting revisions: clarify source; preliminary exploration is allowed, but do not fabricate full UI from README.
5. Attractive desktop screen loses primary action on phone: rework layout preserving UX. Propose any new flow as a UX delta.
6. Liquid Glass: check heterogeneous backgrounds, opaque fallback, absent backdrop-filter and reduced motion; do not attribute Apple's renderer fidelity to web blur.
7. Reference shows only success: derive empty/error/loading from source UX and label our adaptation. Do not attribute hidden states to the reference product.
8. No renderer: deliver local preview as draft with NOT RUN; HTML existence is not visual QA.
9. Next task: read UI/UX indexes and accepted choices, create a new revision and preserve reasons for rejecting/replacing earlier choices.

These are authoring scenarios, not reports of actual user sessions. When implementing the skill, check links/packages/contracts; an actual UI task needs its own render review. Do not call methodological smoke checks usability testing.

10. Design needs a hero illustration: generate it, include in preview and check crops/contrast; unavailable image generation → required asset missing, draft. Authoring the methodology does not require a random hero for palarran itself.
