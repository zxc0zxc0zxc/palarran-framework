# Incident sources and applicability

Public primary sources below were accessed **2026-10-24**. Dates describe source metadata visible at access, not fresh operational evidence. Source owners' practices motivate this guide; Palarran's incident IDs, lane budgets, ACK protocol, lease/fencing rules, evidence gates and VPS SQLite service contract are our engineering design. No source proves that this repository has deployed those capabilities.

| ID / primary source | Publication/version information | Supported basis | Applicability and boundary |
|---|---|---|---|
| G1 [Google SRE: Managing Incidents](https://sre.google/sre-book/managing-incidents/) | Book chapter; accessed page carries ©2017 and notes an earlier article in April 2015 | Explicit operational roles, coordinated changes, living incident record and acknowledged command transfer | Organizational practices adapted for agents/sessions; no Google endorsement or remote-lock implementation implied |
| G2 [Google SRE Workbook: Incident Response](https://sre.google/workbook/incident-response/) | Workbook chapter; no separate last-updated date stated on the accessed chapter | Coordinated response, defined incident roles, contemporaneous debugging record and separation of impact mitigation from cause analysis | Examples are Google/PagerDuty experience, not our measurements; no universal severity/response-time guarantee |
| G3 [Google SRE: Postmortem Culture](https://sre.google/sre-book/postmortem-culture/) | Book chapter; no separate last-updated date stated on accessed content | Blameless analysis, contributing causes, incident impact and preventive follow-ups | Learning framework, not proof that a particular root cause or permanent fix is verified |
| A1 [AWS OPS10-BP01: Event, incident, and problem management](https://docs.aws.amazon.com/wellarchitected/latest/operational-excellence-pillar/ops_event_response_event_incident_problem_process.html) | Living Operational Excellence Pillar documentation; publication/update date not stated on accessed page | Defined response process, roles, severity categories, communications and continued learning | AWS service suggestions do not require purchasing/installing those services or grant access |
| A2 [AWS OPS07-BP04: Use playbooks to investigate issues](https://docs.aws.amazon.com/wellarchitected/latest/operational-excellence-pillar/ops_ready_to_support_use_playbooks.html) | Living documentation; publication/update date not stated | Investigation playbooks, special-permission declarations, escalation and companion mitigation runbooks | Maintained target procedures take precedence over improvised repairs; automation is separate implementation scope |
| A3 [AWS OPS11-BP02: Perform post-incident analysis](https://docs.aws.amazon.com/wellarchitected/latest/operational-excellence-pillar/ops_evolve_ops_perform_rca_process.html) | Living documentation; publication/update date not stated | Timeline milestones, contributing conditions and tracked corrective actions | Supports postmortem structure; no invented timings or automatic attribution of one cause |
| A4 [Amazon: Timeouts, retries, and backoff with jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/) | First-party article; accessed redirect to AWS Builder Center reports published/modified 2019-12-05 | Timeouts can hide completed side effects; retries can amplify overload; idempotency and bounded backoff matter | Our no-blind-replay/aggregate-load protocol is an adaptation; article is not an exactly-once or infrastructure-fencing guarantee |
| S1 [SQLite: Write-Ahead Logging](https://sqlite.org/wal.html) | Living technical documentation; pin/check actual implementation version separately | WAL uses same-host shared state, supports concurrent readers and one writer, and requires checkpoint/durability consideration | Supports a single-host server-side design; not shared network-filesystem SQLite or multi-host consensus |
| S2 [SQLite: Appropriate Uses](https://sqlite.org/whentouse.html) | Living technical documentation; version-specific deployment review still required | Application-server mediation is a viable pattern; direct concurrent network-file access and high writer contention need care | Database suitability does not establish a deployed chat's security, load capacity, backups or availability |

The initially guessed AWS path `ops_learn_post_incident_analysis.html` was inaccessible. It was not used as a source; the canonical OPS11-BP02 page above was opened through AWS's own OPS10-BP01 link. The Amazon legacy URL currently redirects to a first-party Builder Center page; the link above preserves the established entry URL, not an assertion that its hosting location is permanent. No source content was copied as a runbook or executable production command.

The generic runtime contract (`packages/core/orchestration/docs/contract.md`) and operations (`packages/core/orchestration/docs/operations.md`) describe existing bounded orchestration; their lease tokens do not automatically protect remote production actions or supply an incident chat.

Current documentation-only scope: read primary public sources and author [incident workflow](README.md)/[coordination design](coordination.md). No live host/API/DB connections, deployment, package installation, model calls, production probes or service activation were performed as source research. Service implementation/integration proceeds separately; only actual independent receipts establish implemented behavior, and live cross-machine capability remains NOT_VERIFIED without authorized live evidence. Planned tests are not observed capability. Operational use must refresh target-specific version/runbook/source assumptions and record actual evidence separately.
