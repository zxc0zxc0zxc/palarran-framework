# Application code security audit

`/palarran:security:code {scope?}` reviews application security behavior against its actual business rules, data ownership and implementation. Read the [shared audit/evidence contract](../../shared/docs/contract.md), [dated sources](sources.md), target instructions and relevant accepted decisions first. An audit authorizes bounded local source/configuration inspection and public-source research; it does not authorize fixes, installs, application execution, exploit reproduction or remote testing. `--plan` produces only the review/evidence plan from available context without application/scanner execution, remote calls or application/configuration changes. Local source/document inspection and inert private planning artifacts remain allowed.

## Establish the policy and subject

Pin revision plus in-scope dirty-file hashes, language/framework/runtime, deployed-artifact knowledge and unresolved gaps. Read the business process before declaring a control correct. Identify assets, tenants, actors/roles, support/admin/service principals, ownership/membership rules, delegation and permitted lifecycle transitions. If policy is missing, propose it explicitly and ask about the specific unresolved business behavior; do not turn an assumption into a confirmed authorization defect or a claim of safety.

Use an actor×resource×operation matrix with concrete in-scope records, resource states and expected allow/deny outcomes. Include anonymous, user A, user B in the same tenant, user C in another tenant, reduced/expired/revoked membership, service account and privileged role. An API route's login middleware is not its object policy: [OWASP API1:2023](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/) treats user-controlled resource identifiers as a distinct authorization boundary. [Microsoft's resource-based authorization guidance](https://learn.microsoft.com/en-us/aspnet/core/security/authorization/resource-based) is a concrete example of why declarative route authorization may not decide access to a loaded object.

## Follow the full operation

Review entry point → principal verification → policy decision → resource/tenant query → transaction/side effect → response/cache/export. Record exact files/lines and policy source at each hop. Inspect alternate methods/endpoints, asynchronous jobs, administrative operations and internal callers. A search for `Authorize`, `isAdmin`, `tenant_id` or a scanner alert is an index for inspection, not proof of enforcement or a confirmed issue.

| Area | Review questions and edge cases |
| --- | --- |
| Passwords and recovery | How are passwords hashed/salted, work factors selected, legacy hashes migrated and reset/verification tokens scoped? Inspect replay/expiry, account enumeration, recovery privilege, rate-limit design and error behavior. Do not retrieve real hashes/passwords or benchmark/attack authentication automatically. |
| Sessions, tokens and identity | Signature/algorithm/key selection, issuer/audience/expiry, key rotation, session fixation/rotation/logout/revocation, refresh-token reuse, cookie scope/security and service credentials. Distinguish authenticated identity from user-editable metadata. A decoded JWT is not a verified JWT. |
| Object and tenant authorization | Scope reads/writes/deletes/search/export to the caller's permitted resources; include nested/indirect IDs, file/download IDs and batch requests. Check jobs and storage calls retain the same tenant policy. Random IDs do not substitute for access checks. |
| Property authorization and disclosure | Allowlisted mutation fields, server-owned role/owner/tenant/price/approval state, field-level read projection, excessive serialization and accidental exposure in server/client payloads, errors, logs or caches. Valid object access does not permit every property. |
| Function/role authorization | Server-side checks for admin/support/privileged operations, routes added outside normal middleware, delegated actions, token scopes and service-to-service paths. Hidden buttons are not restrictions. |
| Business invariants and races | Atomic authorization+mutation boundary, ownership changes between check/use, concurrent membership removal, duplicate transfers/orders/invites, idempotency scope, retry/rollback and stale caches. Document the violated business invariant and proposed interleaving; do not run concurrent mutations during an audit. |
| Dangerous execution and parsing | Data reaching shell/process arguments, dynamic evaluation/templates/plugins, unsafe deserialization, archive/file access, native/FFI boundaries and outbound requests. Distinguish untrusted-data reachability from dangerous API presence alone. |
| Dependencies and build/runtime boundary | Direct/transitive/optional/dev dependencies, plugins, CI actions, lockfiles, generated/bundled/vendored code and image/runtime mismatch. Send advisory applicability to the [CVE profile](../../cve/docs/README.md); do not equate an old version with a proven exploit. |

The [OWASP password storage guide](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) supports adaptive password hashing rather than plaintext or fast generic hashes. Record the actual algorithm/parameters and platform constraints; select target-specific cost measurements in a separately authorized implementation/test plan. Never write secret values to findings. For deserialization, the [Python pickle documentation](https://docs.python.org/3/library/pickle.html) provides a specific unsafe-untrusted-data example; apply equivalent framework/vendor guidance to the installed stack rather than assuming all serialization formats have identical execution behavior.

## Cross-user and tenant cases are mandatory proposals

For each relevant object operation, define at least: owner allowed; same-tenant other user denied unless policy grants it; other-tenant user denied; anonymous/expired/revoked actor denied; privileged exception scoped by actual policy. Cover read and update/delete separately, nested child→parent mismatches, batch lists mixing allowed/denied IDs, filters/pagination counts, export/download/presigned links, guessed and legitimate IDs, and property changes such as owner/tenant/role. Include a legitimate control case and the expected absence of unauthorized data **and** persistent side effects. Explicit N/A needs evidence and a policy reason; absent tests remain NOT_RUN.

Example **test design**, not an executed claim: user A owns a synthetic invoice, user B shares the tenant without invoice access, and user C belongs to a different tenant. Propose read/update/download cases for B and C and an allowed read for A. Verify response projection plus state consistency if an isolated authorized harness later exists. Do not borrow real customer records, enumerate live IDs or grant test roles automatically. A `403` alone does not establish no prior side effect, and a `404` alone does not establish correct isolation.

For race risks, record both actors, resources, transaction/locking boundaries, the exact interleaving and invariant. A stale ownership check followed by an unrestricted write may be a source-confirmed control gap; deployment-specific exploitability remains qualified. A planned concurrency test is not a measured race or a performed fix.

## Adapt to the real stack

For Go, inspect middleware composition, context propagation, explicit resource queries, process execution and archive/path handling. For PHP, inspect route policies, request-to-model binding, templating and unsafe object deserialization. For TypeScript/Next.js, trace server actions/route handlers/data-access layers and client projections; [Vercel documents](https://nextjs.org/docs/app/guides/data-security) independent action authorization rather than trusting page-level access. For Python, inspect decorators/dependencies, query scoping, template/serialization and subprocess boundaries. For Rust, inspect extractor/handler policy coverage, unsafe/FFI and filesystem/process paths. Memory safety or static typing does not prove business authorization. Use installed-version official guidance for findings; these are search directions, not automatic vulnerability verdicts.

## Findings and completion

Use the shared finding format with source location, actor/preconditions, violated policy/invariant, input-to-sensitive-operation trace, impact, evidence state, uncertainty and proposed remediation/verification. Prioritize cross-tenant access, privileged takeover and irreversible data effects using actual exposure and preconditions, not labels alone. Keep source-confirmed absence of a required check separate from untested runtime exploitation. Preserve disproving evidence and reasons for rejected candidates.

Deliver coverage by module/operation/control, cross-user test proposals, dependency handoff, gaps and remaining review ownership. No claim that the application is secure because the linter passed or no patterns matched. Save accepted rationale, index and handoff in the **target** private `.palarran/security/` area; project `languages.docs` controls generated artifacts. Fix implementation belongs to a separate explicitly authorized build task, with these finding IDs and independent acceptance gates.
