# Application code security audit

Start with the [task context entry](../../../../core/agents/docs/task-context.md); a small audit uses summary+report with inline decisions. Read only the [selected profile method](../../docs/README.md), applicable [source rows](../../docs/sources.md), [shared findings/schema sections](../../../shared/docs/contract.md), [security domain section](../../../../core/agents/docs/domain-contracts.md#target-security-audits), [compact decision rule](../../../../core/agents/docs/decision-memory.md#small-scoped-reviews) and [short memory entry](../../../../core/agents/docs/global-memory.md#short-entry). Reuse unchanged context in the same task; do not recursively load every linked guide.

`/palarran:security:code {scope?}` reviews the actual business process and code, with finite scope from current project context when omitted. `--plan` allows local inspection/inert private planning only, no application/scanner execution, remote/search-provider calls, fixes or installs. Default is readonly source/configuration review and public-source research. A test plan never grants traffic, exploit or mutation permission.

1. Pin revision/dirty snapshot, stack and actual vs unknown runtime identity. Establish actors, tenants, ownership/delegation, sensitive resources, role permissions and allowed lifecycle transitions. If business policy is unclear, ask about that operation rather than inventing an access rule.
2. Follow actual entry points through verified identity, authorization, data access/transactions, side effects and response/cache projection. Review password hashing/recovery; session/token scope, verification, rotation/revocation; object/tenant/property/function checks; unsafe process/eval/deserialization/file/native/dependency paths. Adapt to the installed stack using the guide's source cases.
3. Propose controlled owner/same-tenant-other/other-tenant/anonymous/revoked/privileged cases for relevant read/write/delete/batch/export/download operations, with nested-ID/property mismatches and legitimate controls. Inspect authorization/use races, idempotency and retry/transaction invariants. Source review may confirm a missing control; successful exploitation and no-side-effect assertions need separately authorized evidence. No real customer IDs, credentials, hashes or raw request bodies in reports.
4. Review candidates contextually; a UUID, login decorator, static type, scanner hit or missing alert cannot decide safety. Hand current dependency applicability to the CVE profile without inventing IDs/fixes. Deduplicate related boundary issues. Use shared coverage PASS/FAIL/NOT_RUN/NA, confidence confirmed/suspected and impact-based severity, preserving counterevidence and gaps.
5. Deliver the shared structured report and concise summary with exact subject/locations/evidence/sources, remediation proposals and reproducible safe retests. Report structural validation separately from security conclusions. Preserve accepted decisions before dependent changes, report revisions, index and handoff under target `.palarran/security/<task>/`, prose in `languages.docs`. Actual fixes, installs, live tests, exploits, paid calls, uploads and publication require their separate existing scope; global learning follows owner policy and privacy review.
